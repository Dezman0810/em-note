# Чеклист: Windows → GitHub → VPS

Краткий порядок действий и **фразы для ассистента**, чтобы не путать контуры и типы изменений.

## Контуры

| Контур | Роль |
|--------|------|
| **GitHub** | Единственный «источник правды» для кода и образов (Actions → GHCR). |
| **Любой из ПК (Windows)** | `git pull` → правки → проверка в Docker → по твоей команде **коммит и push**. Три ПК — одна и та же схема. |
| **VPS (Timeweb)** | Берёт изменения **из репозитория и/или готовых образов** (`git pull`, `docker compose pull`, скрипты из `deploy/`). Секреты только в `.env` на сервере. |

---

## Базовый цикл (запомнить порядок)

1. **Синхронизация:** `git pull origin main` (или своя ветка → потом merge в `main`).
2. **Правки + проверка** в Docker на Windows (см. ниже «какой compose»).
3. **Перед коммитом:** нет ли в диффе секретов (`.env`, ключи, пароли); `git status` осмысленный.
4. **Коммит и push** в GitHub — только когда ты явно просишь (или по твоему правилу в Cursor).
5. **VPS:** дождаться успешного **Publish Docker images** в Actions (если менялись образы), затем на сервере обновление (`deploy/vps-update.sh` или `remote-update-vps` — см. [README.md](README.md)).

## Какой Docker на Windows

| Задача | Файл | URL |
|--------|------|-----|
| Разработка UI (Vite, быстрый цикл) | `docker-compose.yml` | UI: http://localhost:8080 · API: http://localhost:8000/docs |
| Как «на проде» (nginx + собранный фронт) | `docker-compose.prod.yml` | http://localhost:8080 (порт меняется через `COMPOSE_WEB_PORT`) |

Для сборки **`docker-compose.prod.yml`** на Windows в репозитории есть `.dockerignore` (не тащить `frontend/node_modules` в контекст билда).

## Что писать ассистенту (шпаргалка фраз)

Одна задача — одна явная формулировка. Можно копировать и дополнять контекстом.

| Цель | Пример формулировки |
|------|---------------------|
| Поднять dev-стек после `git pull` | «Подними `docker-compose.yml`, проверь что API и UI открываются.» |
| Проверить как на проде (nginx, лимиты тела запроса) | «Подними `docker-compose.prod.yml`, проверь `/health` и [сценарий].» |
| Закрепить код в GitHub | «Сделай коммит: [кратко зачем]. Пуш не делай» / «… и запушь в `main`.» |
| Только VPS, код уже в `main` | «Выкати на VPS: `git pull` + образы через `vps-update.sh`» или «Обнови сервер по SSH как в deploy/README». |
| Смесь: правки + коммит + выкладка | По шагам: сначала «внеси X и проверь в Docker», потом отдельно «закоммить и запушить», потом «обнови VPS». |
| Откат / без коммита | «Только локально правь, без коммита» / «Откати несохранённые изменения в файле …». |

Если нужна **ветка**, скажи явно: «Сделай ветку `feature/…`, коммиты туда» — и отдельно про merge на GitHub или локально.

## Типы изменений → что проверить и что выкатывается

| Тип | Где |
|-----|-----|
| Только фронт | После push пересобирается образ **`em-note-web`**; на VPS нужен `pull`/`up` веб-образа (или полный prod compose). |
| Только бэкенд | Образ **`em-note-api`**; на VPS обновление API + миграции при старте контейнера. |
| Nginx / `deploy/Dockerfile.web` | Попадает в **web**-образ; проверка через **`docker-compose.prod.yml`**. |
| `docker-compose*.yml` на сервере | На VPS обязателен **`git pull`**, затем `compose up` с нужным файлом. |
| Секреты, SMTP, JWT | Только **`backend/.env`** (локально) и **корневой/серверный `.env`** на VPS — **не в Git**. |
| Новые зависимости npm/pip | Пересборка образа (`--build` или Actions). |

---

## VPS (Timeweb): не забыть

- После push в `main` дождаться зелёного workflow **Publish Docker images**, иначе `docker pull` скачает старый тег.
- Если перед Docker стоит **панельный nginx** у провайдера — лимиты (например размер тела запроса) настраиваются **там**, не только в `deploy/nginx/docker-prod.conf`.
- Подробные команды: [deploy/README.md](README.md) (обновление, SSH, диагностика).

## Мини-чеклист перед коммитом

- [ ] Нет `backend/.env` и прочих секретов в индексе.
- [ ] Понятное сообщение коммита (зачем изменение).
- [ ] Для образов: после push проверить Actions.
- [ ] Для VPS: выполнить шаг обновления на сервере.

Если нужно, этот файл можно дополнять под ваши внутренние договорённости (ветки, код-ревью, теги релизов).
